\begin{abstract}
Software increasingly reaches phones, browsers and embedded devices as portable intermediate code, often as small plug-ins and over-the-air updates, where every byte counts. Three-address code is verbose: literals sit in fresh temporaries, values are recomputed, and dead branches survive. Existing work either shrinks native code inside large production compilers or compresses intermediate code as an opaque file with Brotli, Zstandard or xz, and reported savings rarely separate optimization from encoding. We present a pipeline that converts three-address code to static single assignment form, runs seven passes, including sparse conditional constant propagation and copy propagation, to a fixed point, and writes a self-describing bytecode with variable-length operands. We evaluate seven demonstration programs and ten C kernels that read input and call functions, checking every result with independent decoders, reference interpreters and differential testing. Optimization removed \nredSMin\% to \nredSMax\% of the instructions of the demonstration programs, but only \nredKMin\% to \nredKMax\% of the kernels. Against the best of Brotli, Zstandard and xz applied to the same optimized program as text, the bytecode was \ncmpFramedSMin\% to \ncmpFramedSMax\% smaller on the demonstration programs and \ncmpFramedKMin\% to \ncmpFramedKMax\% smaller on the kernels; with a shared dictionary, the compressors won on \ndictLosersCount{} of the seven small programs. Canonical Huffman coding paid off above about \nhuffHi{} bytes. Differential testing showed that the first release miscompiled \ndiffReleasedDiffer{} of \ndiffPrograms{} random programs (\ndiffReleasedRate\%) by folding division with floor semantics; the corrected pipeline agrees on all of them. Future work will add arrays and pre-trained entropy models.
\end{abstract}

\section{Introduction}
\label{sec:introduction}
%% ===========================================================================
\PARstart{P}{ortable} intermediate code has become a common way to deliver software. Embedded and Internet of Things (IoT) devices receive new functionality through over-the-air updates, where every transmitted byte costs radio energy and every stored byte costs flash memory~\cite{bauwens2020ota}. Web browsers execute WebAssembly modules, a standardized portable bytecode~\cite{w3c2019wasm}, whose performance and deployment have been studied on large application suites~\cite{jangda2019wasm}. Compiler infrastructures such as MLIR keep programs in several levels of intermediate representation (IR) before any machine code is produced~\cite{lattner2021mlir}. Most of these representations build on static single assignment (SSA) form, in which every variable is defined exactly once~\cite{rastello2022ssa}.

The problem studied in this article is the size of such intermediate code when it must be stored or sent. A straightforward lowering of a C-like program to three-address code (TAC) is verbose. Every literal is placed in a fresh temporary, expressions whose operands are compile-time constants are left for run time, and branches that can never be taken are kept. Our motivation is practical. A teaching compiler built by our team, called IR (intermediate representation) Compression Studio, reported large end-to-end savings, but it was unclear how much of each saving came from optimization, how much from the binary format, and whether every reported number and every optimization was correct. Small programs make the question sharper, because fixed per-file costs such as coder tables and container headers can outweigh the payload. Programs whose values are all known at compile time make it misleading, because optimization then removes almost everything.

Existing methodologies attack program size from two directions. The first direction transforms the program. Classic scalar optimizations such as constant propagation, value numbering and dead-code elimination are textbook material~\cite{cooper2022eac}, and SSA form makes them sparse and fast~\cite{rastello2022ssa}. Production compilers add size-specific transformations and increasingly choose among them with machine learning~\cite{wang2018ml,ashouri2018autotuning}.

The second direction encodes the program compactly after it has been produced. Entropy coders such as Huffman codes assign short bit strings to frequent symbols and are still widely used inside larger compressors~\cite{moffat2019huffman}. General-purpose compressors combine such coders with string matching and can be applied to any IR file without knowing what it contains.

Both directions have shortfalls for small intermediate programs. Size-oriented compiler transformations, such as function merging, loop rolling, inlining and outlining~\cite{rocha2020salssa,rocha2021hyfm,rocha2022rolag,damasio2021inlining,theodoridis2022inlining,chabbi2021ios}, are built into large production toolchains and are evaluated on native binaries of whole applications, so their gains are hard to reproduce in a small educational compiler or to separate from the binary format. Machine-learned approaches~\cite{trofin2021mlgo,jain2022posetrl,cummins2023llm,cummins2021compilergym,cummins2021programl} add training infrastructure and models that are larger than the programs they optimize.

General-purpose compressors are blind to program semantics. They cannot remove an instruction that is never executed, and on inputs of a few hundred bytes their containers and coding tables are a large fraction of the output. Neither direction routinely checks that the transformed program still behaves like the original, although compilers are known to contain miscompilation bugs that only systematic testing reveals~\cite{chen2020testing}.

This article proposes an SSA-based compaction pipeline that optimizes first and encodes second. The program, which may define functions and read input, is lowered to TAC, converted to semi-pruned SSA form and optimized with seven passes iterated to a fixed point: constant folding and propagation, sparse conditional constant propagation (SCCP)~\cite{wegman1991sccp}, copy propagation, dominator-scoped value numbering, dead-code elimination, CFG simplification and trivial-$\phi$ removal. The optimized code is then written as a compact, self-describing bytecode, which we call \clir{}, using one opcode byte and Little Endian Base 128 (LEB128) operands~\cite{w3c2019wasm}. Its constant pool holds exactly the literals the code refers to, and it can be followed by a canonical Huffman coder~\cite{schwartz1964canonical} or replaced by a column-oriented container. The approach is apt because the programs are small and many of their values are known at compile time, which is where removing instructions beats compressing them; programs that read input show how much of that advantage remains.

The main advantage of the proposed work is that its claims are checked rather than assumed. Every number in this article is produced by evaluation scripts released with the compiler. Every encoding is decoded without any table from the encoder and executed again; the behavior of every program is compared by reference interpreters, by native compilation of the kernels and by differential testing. The contributions are: 1) a reproducible SSA compaction pipeline with seven passes and an exact, self-describing byte layout; 2) an evaluation on seven demonstration programs, ten C kernels that read input and call functions, and random programs, which separates the effect of optimization from that of encoding by compressing the same optimized program with Brotli, Zstandard and xz, with and without container headers and shared dictionaries; 3) a comparison with Java class files and LLVM bitcode; 4) a break-even model for static Huffman coding that shows the effect of the header design; and 5) a differential-testing campaign that measured the severity of a constant-folding defect and confirmed its fix.

The rest of the manuscript is structured as follows. Section~\ref{sec:related} reviews fifteen related works and earlier work on code and bytecode compression. Section~\ref{sec:proposed} formulates the problem and presents the architecture, methodology, modules, flow, equations and algorithms of the proposed system. Section~\ref{sec:results} describes the implementation tools, parameter setup and performance metrics, and analyzes the results against existing compressors. Section~\ref{sec:conclusion} concludes and outlines future work.

\section{Related Works}
\label{sec:related}
%% ===========================================================================
This section reviews fifteen recent works in four groups: compiler transformations that reduce code size, machine-learning-guided optimization, studies of portable bytecode, and compiler correctness. For each work we summarize the proposed solution, the methodology and tools, the results, and the research gap that remains for compact intermediate code. Table~\ref{tab:related} gives an overview. Section~\ref{sec:codecompression} then summarizes the earlier literature on code and bytecode compression and the binary formats of WebAssembly, LLVM and the Java virtual machine, with which our encoding is compared in Section~\ref{sec:results}.

\subsection{Code-Size Reduction by Compiler Transformations}

\subsubsection{SalSSA, function merging in SSA form}
\textit{Solution.} Rocha \textit{et al.}~\cite{rocha2020salssa} proposed SalSSA, which merges similar functions into one while staying in SSA form, so that the register demotion required by the earlier FMSA approach is no longer needed. The merged control-flow graph is built top-down from the two input graphs, and a $\phi$-node coalescing step reduces the extra code that merging introduces.

\textit{Methodology and tools.} Each function is linearized into labels and instructions, and a sequence alignment pairs matching instructions. $\phi$-nodes travel with their block labels, mismatched operands are chosen with a \texttt{select} on a function identifier, and the operands of commutative instructions are reordered to avoid selects.

SalSSA was implemented in LLVM 11 and evaluated on SPEC CPU2006 and CPU2017 on an Intel x86 machine, and on MiBench for ARM Thumb, against FMSA. Object size, compile time, peak memory and run time were measured over five repetitions.

\textit{Results.} Code size fell by 9.3\% to 9.7\% on SPEC CPU2006 and 7.9\% to 9.2\% on CPU2017, about twice the reduction of FMSA. Compile-time overhead was about 5\% instead of 14\%, and memory use roughly halved.

\textit{Research gap.} The work targets whole functions in native binaries; it does not consider how the remaining IR is encoded.

\subsubsection{HyFM, hybrid function merging}
\textit{Solution.} HyFM~\cite{rocha2021hyfm} aligns functions block by block instead of as whole instruction sequences. A multi-tier profitability analysis discards unprofitable block pairs before any merged code is generated.

\textit{Methodology and tools.} Blocks and functions are summarized by vectors of opcode counts, paired by Manhattan distance, and aligned either with the Needleman--Wunsch algorithm or with a linear pairwise alignment of equal-sized blocks. The first tier compares the estimated cost of each block pair before and after merging.

HyFM was implemented in LLVM 11, the same version as SalSSA, and evaluated on SPEC CPU2006 and CPU2017 on an Intel Xeon machine with five repetitions. Code size, merging time, compile time and peak memory were reported.

\textit{Results.} With pairwise alignment, the code-size reduction stayed within one percentage point of SalSSA, while function merging ran 4.59 to 5.28 times faster on average and peak memory dropped from 2.4~GB to about 610~KB.

\textit{Research gap.} Block pairing is still quadratic in the number of blocks, and the work remains specific to native code.

\subsubsection{RoLAG, loop rolling}
\textit{Solution.} RoLAG~\cite{rocha2022rolag} rolls isomorphic straight-line code back into loops. It finds repeated code by aligning SSA graphs bottom-up from seed instructions such as stores and calls.

\textit{Methodology and tools.} Mismatching values become loop inputs, and special patterns such as monotonic integer sequences, chained dependences and reduction trees widen the code that can be aligned. A scheduling analysis checks that reordering is legal, and a profitability analysis based on LLVM's code-size cost model keeps the smaller version.

RoLAG was built on LLVM 12 and evaluated with \texttt{-Os} on about one million AnghaBench functions, on MiBench and SPEC CPU2017 programs, and on the TSVC kernels, against LLVM's loop-rerolling pass.

\textit{Results.} Affected AnghaBench functions shrank by 9.12\% on average, and the largest absolute saving on full programs was 87.91~KB. On TSVC, RoLAG reduced size by 23.4\% against 13.69\% for LLVM.

\textit{Research gap.} Rolling works only inside a single basic block and can be unprofitable when the cost model misses later passes.

\subsubsection{Inlining for code size}
\textit{Solution.} Dam\'asio \textit{et al.}~\cite{damasio2021inlining} showed that inlining, usually seen as a code-growing transformation, can shrink code. They inline functions that have a single call site and then delete the original, and they search for calls at which inlining lets the compiler simplify the body for that particular caller.

\textit{Methodology and tools.} The first technique is a simple heuristic over the call graph. The second is an analysis that estimates whether specializing the callee to the constants at a call site will remove code.

Both techniques were implemented in LLVM and evaluated on MiBench against \texttt{clang -Os}, with running time compared statistically.

\textit{Results.} Code size fell by 2.96\% on average and by up to 11\%, with no statistically significant change in running time.

\textit{Research gap.} The evaluation covers one benchmark suite and native code only.

\subsubsection{Optimal function inlining}
\textit{Solution.} Theodoridis \textit{et al.}~\cite{theodoridis2022inlining} studied how far LLVM's inliner is from optimal when optimizing for binary size and derived an autotuning strategy from the findings.

\textit{Methodology and tools.} A formulation of the inlining problem shrinks the search space enough to evaluate every inlining choice exhaustively for 1135 SPEC2017 files.

The autotuner was then applied to SPEC2017, the LLVM code base and SQLite, with LLVM's heuristic as the baseline.

\textit{Results.} The authors report an average improvement of 7\% (up to 28\%) over LLVM on SPEC2017, 15\% on LLVM's own code and 10\% on SQLite.

\textit{Research gap.} The study focuses on one transformation in a production compiler and does not address the encoding of portable code.

\subsubsection{Code-size optimization of production iOS applications}
\textit{Solution.} Chabbi \textit{et al.}~\cite{chabbi2021ios} reduced the size of a production iOS application written in Swift and Objective-C with whole-program machine-code outlining, repeated over several rounds.

\textit{Methodology and tools.} An analysis pass logged repeated instruction sequences and traced them to causes such as reference-counting calls, frame setup and copies produced when leaving SSA form.

All modules were compiled to LLVM IR, linked with \texttt{llvm-link}, optimized and then outlined as one program, using Swift 5.2, Xcode and patched LLVM for AArch64 devices, with production data from millions of users.

\textit{Results.} The code section of the UberRider application shrank by 23\% (114.5~MB to 88.4~MB) and the whole binary by 17.6\%; the Linux kernel and Clang shrank by 14\% and 25\%. Release builds took 66 instead of 21 minutes.

\textit{Research gap.} The approach needs a custom toolchain and much longer builds, and it works on machine code rather than on portable IR.

\subsection{Machine-Learning-Guided Optimization}

\subsubsection{MLGO}
\textit{Solution.} MLGO~\cite{trofin2021mlgo} is a framework for using machine-learned policies inside LLVM. Its first application replaces the heuristic in LLVM's inlining-for-size pass.

\textit{Methodology and tools.} Inlining is modeled as a sequential decision process with eleven numerical features of caller, callee and call graph. Policies are trained with policy gradient, warm-started by imitating the existing heuristic, and with evolution strategies.

Training used TF-Agents on more than 28,000 IR modules of an internal application, and the released model is compiled ahead of time into LLVM, so that compilation stays deterministic.

\textit{Results.} The learned policies reduced size by up to 7\% compared with \texttt{-Oz}, for about 1\% extra compile time.

\textit{Research gap.} The method needs large training infrastructure and targets native size only.

\subsubsection{POSET-RL}
\textit{Solution.} POSET-RL~\cite{jain2022posetrl} uses reinforcement learning to choose the order of optimization passes so that code size and execution time both improve.

\textit{Methodology and tools.} A Double Deep Q-Network observes 300-dimensional IR2Vec embeddings of the program and selects sub-sequences of the \texttt{-Oz} pipeline. These come from a manual grouping or from an Oz Dependence Graph. The reward combines object-size reduction with throughput estimated by LLVM-MCA.

The agent was trained in LLVM 10 on 130 files from the LLVM test suite and evaluated on MiBench, SPEC CPU2006 and SPEC CPU2017 on x86 and AArch64.

\textit{Results.} The graph-based variant improved code size by 6.19\% and execution time by 11.99\% over \texttt{-Oz} on SPEC CPU2017 on average.

\textit{Research gap.} The rewards are proxies, and some benchmarks grew or slowed down.

\subsubsection{Large language models for compiler optimization}
\textit{Solution.} Cummins \textit{et al.}~\cite{cummins2023llm} trained a 7-billion-parameter transformer to read unoptimized LLVM IR and emit a list of passes that minimizes the instruction count.

\textit{Methodology and tools.} The model follows the Llama~2 architecture and was trained from scratch on one million LLVM-IR functions (about 373 million tokens). Auxiliary tasks ask it to predict instruction counts and the optimized code.

Training labels came from an autotuner that ran tens of thousands of compilations per program. Evaluation used 100,000 unseen functions and compared the model with AutoPhase and Coreset-NVP.

\textit{Results.} The model's pass lists produced 3.01\% fewer instructions than \texttt{-Oz} without extra compilations, and its generated code compiled 90.3\% of the time.

\textit{Research gap.} The model cannot reliably fold constants, its context is limited to 2048 tokens, and inference is far slower than compilation.

\subsubsection{CompilerGym}
\textit{Solution.} CompilerGym~\cite{cummins2021compilergym} packages compiler optimization tasks as reinforcement-learning environments with the OpenAI Gym interface.

\textit{Methodology and tools.} A Python front end talks to compiler services over remote procedure calls. Environments cover LLVM phase ordering with 124 passes, GCC flag tuning and CUDA loop nests. Observations range from instruction counts to graph representations, and rewards include IR instruction count relative to \texttt{-Oz}.

More than one million LLVM benchmarks are bundled, and the framework validates semantics with differential testing and sanitizers.

\textit{Results.} An environment step took 7.5~ms instead of 205.9~ms in earlier work, about 27 times faster. The best autotuner reached 1.083 times the code-size reduction of \texttt{-Oz} on cBench.

\textit{Research gap.} It is an experimentation platform, and its learning agents generalized poorly across program domains.

\subsubsection{ProGraML}
\textit{Solution.} ProGraML~\cite{cummins2021programl} is a language-independent graph representation of programs for machine learning, combining control, data and call relations in one multigraph.

\textit{Methodology and tools.} Instructions, identifiers and immediate values become vertices built from LLVM or XLA IR, with typed and ordered edges. A message-passing neural network learns over the graph.

Classic data-flow analyses such as reachability, dominators and liveness were posed as supervised learning tasks on a large dataset of IR files, and the representation was then applied to downstream optimization tasks.

\textit{Results.} The authors found that earlier learned representations struggle to reproduce data-flow analyses and that ProGraML improves results on downstream tasks.

\textit{Research gap.} It learns analyses that a compiler can compute exactly, and it does not produce compact program encodings.

\subsection{Studies of Portable Bytecode}

\subsubsection{Real-world WebAssembly binaries}
\textit{Solution.} Hilbig \textit{et al.}~\cite{hilbig2021wasm} conducted a large empirical study of WebAssembly binaries found in the wild.

\textit{Methodology and tools.} The authors collected 8461 unique binaries from source repositories, package managers and live websites.

They analyzed source languages, security-relevant imports and use cases, and released the collection, 58 times the size of any WebAssembly benchmark used before.

\textit{Results.} Two thirds of the binaries were compiled from memory-unsafe languages, 21\% imported potentially dangerous host functions, and 29\% of the binaries on websites were minified.

\textit{Research gap.} The study characterizes binaries but does not try to make them smaller.

\subsubsection{Superoptimization of WebAssembly bytecode}
\textit{Solution.} Cabrera Arteaga \textit{et al.}~\cite{cabrera2020superopt} superoptimized WebAssembly code by inserting the Souper superoptimizer into an LLVM-to-WebAssembly pipeline.

\textit{Methodology and tools.} C programs were compiled with Clang at \texttt{-O3} to LLVM bitcode, passed through Souper, which proves replacements equivalent with an SMT solver, and linked to WebAssembly.

Four Souper configurations with a 300-second timeout were tried on 12 Rosetta Code programs, and the instruction counts of the resulting modules were compared.

\textit{Results.} The median reduction was 0.33\% of the instructions. One program shrank from 45 to 21 instructions, and one program grew.

\textit{Research gap.} The cost model works on LLVM IR rather than on the final bytecode, and the evaluation is small.

\subsection{Compiler Correctness}

\subsubsection{Alive2}
\textit{Solution.} Alive2~\cite{lopes2021alive2} checks automatically, without changes to LLVM, that each optimized function refines the original one, a technique known as translation validation.

\textit{Methodology and tools.} Source and target functions are encoded for the Z3 SMT solver with LLVM's forms of undefined behavior. Loops are unrolled to a bound, which keeps checking fast but means some bugs are missed.

The tool was run over the functions in LLVM's unit-test suite that exercise IR-level transformations.

\textit{Results.} The tool exposed 47 previously unknown bugs, of which 28 had been fixed at the time of writing, and led to eight corrections of the LLVM language reference.

\textit{Research gap.} The approach depends on a full formal semantics of the IR and on a solver, which a small compiler does not have.

\subsubsection{YARPGen}
\textit{Solution.} YARPGen~\cite{livinskii2020yarpgen} generates random C and C++ programs that are free of undefined behavior and uses them for differential testing of compilers.

\textit{Methodology and tools.} The generator tracks values while generating and rewrites operations that could trigger undefined behavior; the rewrite rules were checked exhaustively on 4-bit values and with Z3.

Generation policies steer programs toward patterns that trigger specific optimizations. The compilers under test were GCC, LLVM and Intel's C++ compiler, all targeting x86-64.

\textit{Results.} YARPGen found 83 new bugs in GCC, 62 in LLVM and 76 in the Intel compiler, and its policies triggered targeted optimizations 20\% (LLVM) and 40\% (GCC) more often.

\textit{Research gap.} It tests production C compilers, not the compactness or losslessness of IR encodings.

\subsection{Code and Bytecode Compression}
\label{sec:codecompression}
Compact program representations were studied intensively before the works above. Ernst \textit{et al.}~\cite{ernst1997code} derived two formats from the intermediate code of a C compiler: an interpretable format that can be executed without decompression and a denser wire format that is expanded before execution, and compared both with general-purpose compression of native code. Franz and Kistler~\cite{franz1997slim} distributed programs as \emph{slim binaries}, abstract syntax trees compressed with an adaptive dictionary from which native code is generated at load time. Pugh~\cite{pugh1999java} reorganized the class files of a Java archive, sharing constants across classes and storing each kind of data in its own stream, before applying a general-purpose compressor. Lucco~\cite{lucco2000split} split machine instructions into separate streams for opcodes, registers and immediates and compressed each with its own dictionary, which is the idea behind our columnar container. Evans and Fraser~\cite{evans2001grammar} inferred a grammar for bytecode from training programs and rewrote programs into specialized instructions, and Debray \textit{et al.}~\cite{debray2000compaction} combined whole-program optimization with procedural abstraction to compact native binaries.

These works pursue the same goal as ours but mostly on native code or on full Java archives, and they do not separate the contribution of optimization from that of encoding. Among current formats, the WebAssembly binary format~\cite{w3c2019wasm,haas2017wasm} encodes a stack machine with structured control flow and stores integers as LEB128, as \clir{} does. LLVM bitcode~\cite{llvm2024bitcode} is a bit-level stream with variable-width fields, abbreviations and relative value numbers, and the Java class file~\cite{lindholm2023jvm} combines a constant pool with stack-machine bytecode and fixed-width indices. Table~\ref{tab:formats} compares their design with \clir{}, and Section~\ref{sec:formats} compares their sizes.

\subsection{Summary of the Research Gap}
The reviewed works either transform native code inside large production toolchains, learn optimization policies with substantial infrastructure, study bytecode without shrinking it, test compilers without looking at encodings, or compress code without separating optimization from encoding. None of them measures, at the level of a small IR, how much of a size reduction comes from optimization and how much from the binary format, or compares such a pipeline with general-purpose compressors applied to the \emph{same} optimized program while checking that program behavior is preserved. The proposed work addresses this combination.

\subsection{Problem Formulation}
Let $P$ be a source program and $T=\langle t_1,\dots,t_n\rangle$ the three-address code produced for it. For an input sequence $I$, the observable behavior $\mathrm{Obs}(T,I)$ is the sequence of printed values together with the returned value; we write $\mathrm{Obs}(T)$ when the input is fixed. The goal is to find an optimized instruction list $T^\ast$ and an encoding $E$ that minimize the encoded size while keeping the behavior and allowing the instructions to be decoded:
\begin{equation}
\begin{aligned}
&\min_{T^\ast,\,E}\ |E(T^\ast)|\\
&\ \text{s.t.}\quad \mathrm{Obs}(T^\ast)=\mathrm{Obs}(T),\quad D\big(E(T^\ast)\big)\cong T^\ast,
\end{aligned}
\label{eq:objective}
\end{equation}
where $D$ is the decoder and $\cong$ denotes equality up to a consistent renaming of variables and labels.

The decoder must need nothing but $E(T^\ast)$; in particular, no table kept by the encoder. The problem is split into two stages so that each can be measured on its own. The first stage reduces $n$ to $n^\ast=|T^\ast|$ with semantics-preserving transformations on SSA form. The second stage chooses $E$ among a compact bytecode, the same bytecode with canonical Huffman coding, and a column-oriented container. The reduction obtained by each stage is reported separately, and the constraint on $\mathrm{Obs}$ is checked by executing $T$ and $T^\ast$ with independent interpreters.

Fig.~\ref{fig:architecture} shows the architecture of the proposed system. The front end turns source text into tokens, an abstract syntax tree and TAC, and it fills a scoped symbol table and a constant pool. The middle end builds the control-flow graph (CFG), computes dominance information, converts the code to SSA form and optimizes it. The back end writes the optimized code in three encodings.

\subsection{Detailed Methodology}

\subsubsection{Front end and three-address code}
The input language provides \texttt{int}, \texttt{float}, \texttt{string} and \texttt{bool} variables, arithmetic, relational and logical operators, \texttt{if}/\texttt{else}, \texttt{while} and \texttt{for} statements, nested blocks, a \texttt{print} statement, function definitions and calls (recursion included), and input with \texttt{input()} or \texttt{scanf}. Simple C programs are accepted as well: preprocessor lines are skipped, the body of \texttt{int main()} is the main program, \texttt{printf} is mapped to \texttt{print}, and \texttt{scanf("\%d", \&x)} reads one integer into \texttt{x}. Arrays and pointers are not supported. The TAC generator emits quadruples over 28 opcodes and loads every literal into a fresh temporary, so \texttt{int a = 10 + 20 * 3;} becomes six instructions. Every function other than the main program becomes its own unit, which starts with one \texttt{param} instruction per parameter; calls are \texttt{call} instructions and input is read by \texttt{read} instructions. All later stages process each unit separately. Temporaries are named so that they cannot coincide with a variable of the program.

\subsubsection{Control-flow graph and dominance}
Basic blocks start at the first instruction, at every jump target and after every jump or return; edges follow jumps, both outcomes of conditional jumps and fall-through. A block $d$ dominates $b$ if every path from the entry $r$ to $b$ passes through $d$. The dominator sets are the greatest fixed point of
\begin{equation}
\mathrm{Dom}(r)=\{r\},\qquad
\mathrm{Dom}(b)=\{b\}\cup\!\!\bigcap_{p\in \mathrm{pred}(b)}\!\!\mathrm{Dom}(p).
\label{eq:dom}
\end{equation}
The immediate dominator of $b\neq r$ is the strict dominator that all other strict dominators of $b$ dominate:
\begin{equation}
\begin{aligned}
\mathrm{idom}(b)&=d\in\mathrm{Dom}(b)\setminus\{b\}\\
&\text{such that}\ \ \mathrm{Dom}(b)\setminus\{b\}\subseteq \mathrm{Dom}(d).
\end{aligned}
\label{eq:idom}
\end{equation}
The dominance frontier of a block $x$ collects the join points where the dominance of $x$ ends:
\begin{equation}
\begin{aligned}
\mathrm{DF}(x)=\{\,y \mid{}& \exists p\in\mathrm{pred}(y):\ x\in\mathrm{Dom}(p)\\
&\wedge\ x\notin \mathrm{Dom}(y)\setminus\{y\}\,\}.
\end{aligned}
\label{eq:df}
\end{equation}
The implementation computes $\mathrm{DF}$ by walking up the dominator tree from each predecessor of a join block until the immediate dominator of the join block is reached~\cite{rastello2022ssa}.

\subsubsection{SSA construction}
A variable receives $\phi$-functions only if it is used in some block before being defined there, which yields semi-pruned SSA form. For such a variable $v$ with definition blocks $S_v$, the $\phi$-functions are placed on the iterated dominance frontier
\begin{equation}
\begin{aligned}
\mathrm{DF}^{+}(S_v)&=\lim_{i\to\infty}\mathrm{DF}_i,\qquad \mathrm{DF}_1=\mathrm{DF}(S_v),\\
\mathrm{DF}_{i+1}&=\mathrm{DF}(S_v\cup \mathrm{DF}_i).
\end{aligned}
\label{eq:idf}
\end{equation}
Variables are then renamed in a depth-first walk of the dominator tree, as listed in Algorithm~\ref{alg:ssa}. Fig.~\ref{fig:ssaexample} shows the result for benchmark S2, which contains an \texttt{if}/\texttt{else} diamond followed by a loop: three $\phi$-functions are inserted, one at the join of the diamond and two at the loop header.

\begin{algorithm}[t]
\caption{Semi-pruned SSA construction}
\label{alg:ssa}
\begin{algorithmic}[1]
\REQUIRE CFG $G$ with dominator tree and frontiers $\mathrm{DF}$
\ENSURE $G$ in SSA form
\STATE $\mathit{Glob}\gets$ variables used in a block before their definition there
\FORALL{$v\in\mathit{Glob}$}
  \STATE $W\gets S_v$ \COMMENT{blocks that define $v$}
  \WHILE{$W\neq\emptyset$}
    \STATE remove a block $x$ from $W$
    \FORALL{$y\in\mathrm{DF}(x)$ without a $\phi$ for $v$}
      \STATE insert $v\gets\phi(\,)$ after the labels of $y$
      \STATE \textbf{if} $y\notin S_v$ \textbf{then} add $y$ to $W$
    \ENDFOR
  \ENDWHILE
\ENDFOR
\STATE \textsc{Rename}$(r)$ \COMMENT{start at the entry block}
\STATE \textbf{procedure} \textsc{Rename}$(b)$
\STATE \quad give each $\phi$ and each definition in $b$ a new version $v_k$ and push it
\STATE \quad replace each use in $b$ by the top of its stack
\STATE \quad fill the $\phi$-arguments of every successor of $b$ for edge $(b,\cdot)$
\STATE \quad \textsc{Rename}$(c)$ for each child $c$ of $b$ in the dominator tree
\STATE \quad pop the versions pushed in $b$
\end{algorithmic}
\end{algorithm}

\subsubsection{Optimization passes}
The optimizer applies seven passes in a loop until a round leaves the program unchanged or ten rounds have run (Algorithm~\ref{alg:opt}). Constant folding rewrites an instruction whose operands are literals into a literal load,
\begin{equation}
\langle r\gets a\odot b\rangle,\ a,b\in\mathcal{L}\ \Longrightarrow\ \langle r\gets \mathrm{eval}_\odot(a,b)\rangle,
\label{eq:fold}
\end{equation}
where $\mathcal{L}$ is the set of literals and $\mathrm{eval}$ follows C: integer division truncates toward zero and the remainder takes the sign of the dividend,
\begin{equation}
a \mathbin{/} b = \operatorname{sgn}(ab)\left\lfloor \frac{|a|}{|b|}\right\rfloor,\qquad a \mathbin{\%} b = a - b\,(a \mathbin{/} b).
\label{eq:cdiv}
\end{equation}
Folding also applies the identities $x+0=x$, $x\cdot1=x$, $x\cdot0=0$ and $x-0=x$, replaces operands defined as literals, and turns a conditional jump on a literal into a jump or a fall-through, removing the dead CFG edge and its $\phi$-arguments. It does not look through $\phi$-functions.

Sparse conditional constant propagation~\cite{wegman1991sccp} closes that gap. It assigns every SSA name $x$ a value $\mathcal{V}(x)$ in the lattice $\top \sqsupset c \sqsupset \bot$ (undetermined, the constant $c$, not constant) and only follows CFG edges found executable; a $\phi$-function takes the meet of the arguments on its executable incoming edges,
\begin{equation}
\mathcal{V}\big(x\gets\phi(\dots,p\!:\!a_p,\dots)\big)=\bigsqcap_{(p,b)\ \mathrm{executable}}\mathcal{V}(a_p),
\label{eq:sccp}
\end{equation}
where $\top\sqcap v=v$, $c\sqcap c=c$, and every other meet gives $\bot$. Input, parameters and call results are $\bot$. Constant definitions become literal loads, constant uses become literals, a branch on a constant becomes a jump or a fall-through, and edges never found executable are removed. Copy propagation then replaces every use of $x$, where $x\gets y$ is a copy, by $y$; in SSA form the definition of $y$ dominates every use of $x$, so the copy becomes dead. Both passes run only on code in SSA form.

Value numbering walks the dominator tree with a scoped table indexed by the key
\begin{equation}
\kappa(i)=\begin{cases}(\mathrm{op},\min(a,b),\max(a,b)) & \mathrm{op}\in\{+,\times,=,\neq\}\\ (\mathrm{op},a,b) & \text{otherwise,}\end{cases}
\label{eq:vn}
\end{equation}
and replaces a later instruction with the same key by a copy of the earlier result, which copy propagation removes in the next round; entries are withdrawn when the walk leaves a subtree, so values never flow between sibling branches. Dead-code elimination repeatedly removes every instruction $i$ without side effects whose result is not used,
\begin{equation}
\mathrm{def}(i)\notin \bigcup_{j}\mathrm{uses}(j)\setminus\{\mathrm{def}(j)\mid j\text{ is a }\phi\}\ \Rightarrow\ \text{delete } i,
\label{eq:dce}
\end{equation}
where a $\phi$-function's use of its own result does not keep it alive; \texttt{print}, \texttt{read}, \texttt{call}, jumps and returns are never removed. CFG simplification deletes unreachable blocks and stale $\phi$-arguments, and trivial-$\phi$ removal turns a $\phi$-function whose other arguments all name one value into a copy.

\begin{algorithm}[t]
\caption{Fixed-point driver of the optimizer}
\label{alg:opt}
\begin{algorithmic}[1]
\REQUIRE CFG $G$ of one function in SSA form
\ENSURE optimized CFG $G$
\FOR{$k = 1$ \TO $10$}
  \STATE $G_0 \gets$ copy of $G$
  \STATE \textsc{FoldAndPropagate}$(G)$ \COMMENT{\eqref{eq:fold}, \eqref{eq:cdiv}}
  \STATE \textsc{SCCP}$(G)$ \COMMENT{\eqref{eq:sccp}; may delete edges}
  \STATE \textsc{PropagateCopies}$(G)$
  \STATE \textsc{ValueNumber}$(G)$ \COMMENT{\eqref{eq:vn}; dominator-tree walk}
  \STATE \textsc{EliminateDeadCode}$(G)$ \COMMENT{\eqref{eq:dce}}
  \STATE \textsc{PruneUnreachable}$(G)$
  \STATE \textsc{RemoveTrivialPhis}$(G)$
  \IF{$G = G_0$}
    \STATE \textbf{break}
  \ENDIF
\ENDFOR
\RETURN $G$
\end{algorithmic}
\end{algorithm}

\subsubsection{Encodings}
The optimized blocks of every function are linearized in order and written as one \clir{} package, whose layout is drawn in Fig.~\ref{fig:layout}(a). Each instruction is one opcode byte followed by its operands as unsigned LEB128 integers, which store seven payload bits per byte. An operand $v$ whose binary form has $\beta(v)$ significant bits, with $\beta(0)=0$, therefore occupies
\begin{equation}
\ell(v)=\max\!\left(1,\left\lceil \beta(v)/7\right\rceil\right)\ \text{bytes}.
\label{eq:leb}
\end{equation}
Variables, labels and blocks are numbered per function in order of first appearance. A value operand is tagged in its lowest bit, $\tau(x)=2r$ for a variable in register $r$ and $\tau(c)=2q+1$ for the literal at index $q$ of the constant pool, so literals that propagation places into instructions are part of the package. The pool is built from the optimized code and holds exactly the literals it refers to, in order of first use; an integer is stored as a zigzag-mapped LEB128 value, a Boolean as a tag byte alone. A $\phi$-argument names its predecessor by block ordinal, and the body lists the blocks of each function, so a decoder can rebuild every CFG and execute the program. With $f$ functions, block counts $b_g$, instruction counts $m_B$ and pool entries of $e_j$ bytes, the package size is
\begin{equation}
\begin{aligned}
|\clir{}| &= 5+\ell(k)+\textstyle\sum_{j=1}^{k} e_j+\ell(f)+\sum_{g=1}^{f}\Big(\ell(b_g)+\sum_{B}\big(\ell(m_B)+\mathit{body}_B\big)\Big),\\
\mathit{body}_B &= \textstyle\sum_{i\in B}\Big(1+\sum_{j=1}^{k_i}\ell(\tau(v_{i,j}))\Big).
\end{aligned}
\label{eq:clir}
\end{equation}

The canonical Huffman stage (Fig.~\ref{fig:layout}(b)) computes a Huffman code for the $k$ distinct byte values of the package, limited to 15 bits, and stores only the code length of each value; the decoder rebuilds the canonical code~\cite{schwartz1964canonical}, in which codes of equal length are consecutive integers in symbol order. The header holds the input length $n$ as LEB128 and the smallest of three length tables: a list of the $k$ symbols with 4-bit lengths, a 32-byte bitmap with 4-bit lengths, or 256 4-bit lengths. For a byte value $s$ of frequency $f_s$ and code length $\ell_s$,
\begin{equation}
\begin{aligned}
|H| &= \underbrace{\ell(n)+\min\!\big(2+k+\lceil k/2\rceil,\ 33+\lceil k/2\rceil,\ 129\big)}_{h\ \text{(header)}} + \left\lceil \frac{1}{8}\sum_{s} f_s\,\ell_s \right\rceil,\\
&\qquad \textstyle\sum_s f_s \ell_s \ge n\,\mathcal{H},
\end{aligned}
\label{eq:huff}
\end{equation}
where $\mathcal{H}$ is the empirical entropy of the input in bits per byte~\cite{moffat2019huffman}. The header never exceeds 132 bytes. The first release stored a 32-bit frequency for each symbol instead, $h=7+5k$ bytes, up to 1287 bytes; Section~\ref{sec:results} reports both. Writing the payload as about $n\mathcal{H}/8$ bytes, coding saves space only when $n(1-\mathcal{H}/8)$ exceeds the header, which gives the break-even size
\begin{equation}
n^{\ast} \approx \frac{h}{1-\mathcal{H}/8}.
\label{eq:breakeven}
\end{equation}
The break-even point is therefore a property of the header design, not of Huffman coding as such.

The columnar container (Fig.~\ref{fig:layout}(c)) splits the instructions of each function into an opcode stream, a flag stream, a stream of distances from each use to its definition, and a stream of literals and labels stored as strings, followed by a front-coded table of source names. A definition is implied by its position $i$, and a use of a value defined at position $d$ stores $\delta=i-d$ in zigzag form, $2\delta$ for $\delta\ge0$ and $-2\delta-1$ otherwise; a loop-carried $\phi$-argument is defined later in the linear order and has $\delta<0$. Each $\phi$-argument and call argument carries its own kind flag. A leading flag byte records whether Huffman coding was applied, which is done only when it makes the container smaller. Algorithm~\ref{alg:enc} summarizes the encoding stage.

\begin{algorithm}[t]
\caption{Encoding with adaptive entropy coding}
\label{alg:enc}
\begin{algorithmic}[1]
\REQUIRE optimized functions $T^\ast_1,\dots,T^\ast_f$ (main first), names $N$
\ENSURE \clir{} package $B$, Huffman package $H$, container $Q$
\STATE $C\gets$ empty constant pool; $\mathit{body}\gets$ LEB128$(f)$
\FORALL{functions $T^\ast_g$}
  \STATE number its variables, labels and blocks from 0
  \STATE append LEB128 of its block count to $\mathit{body}$
  \FORALL{blocks $B$ of $T^\ast_g$, instructions $t\in B$}
    \STATE append the opcode byte of $t$ and $\tau$ of its operands, adding new literals to $C$
  \ENDFOR
\ENDFOR
\STATE $B\gets$ \texttt{"CLIR"} $\Vert$ version $\Vert$ $C$ $\Vert$ $\mathit{body}$
\STATE \textbf{assert} decoding $B$ alone gives $T^\ast_1,\dots,T^\ast_f$ up to renaming
\STATE $H\gets$ \textsc{CanonicalHuffman}$(B)$; \textbf{assert} \textsc{Decode}$(H)=B$
\STATE $S\gets$ per-function opcode, flag, delta and immediate streams and front-coded $N$
\STATE $h\gets$ \textsc{CanonicalHuffman}$(S)$; $Q\gets \mathtt{0x01}\Vert h$ \textbf{if} $|h|<|S|$ \textbf{else} $\mathtt{0x00}\Vert S$
\STATE \textbf{assert} decoding $Q$ gives $T^\ast_1,\dots,T^\ast_f$ up to renaming
\RETURN $B$, $H$, $Q$
\end{algorithmic}
\end{algorithm}

\subsection{Performance Metrics}
Six metrics are used. For a quantity that falls from $a$ to $b$, the reduction is
\begin{equation}
R(a,b) = 100\,\frac{a-b}{a}\ \%,
\label{eq:red}
\end{equation}
which gives the instruction reduction when applied to instruction counts and the size reduction when applied to bytes. The encoding density is the number of bits spent per instruction,
\begin{equation}
\rho=\frac{8\,|X|}{N},
\label{eq:density}
\end{equation}
for a representation $X$ of $N$ instructions. The compilation throughput is $\Theta=n/t$ instructions per second for a program of $n$ raw instructions compiled in time $t$, and the entropy-coding overhead is the share $h/|H|$ of the header in \eqref{eq:huff}. Correctness is measured by the agreement rate
\begin{equation}
A=100\,\frac{|\{P:\ \mathrm{Obs}(T_P^\ast,I_P)=\mathrm{Obs}(T_P,I_P)\}|}{|\{P\}|}\ \%
\label{eq:agree}
\end{equation}
over a set of programs $P$ with inputs $I_P$. \emph{Raw TAC text} denotes the unoptimized instructions, one per line, in UTF-8, with a header line \texttt{func f(a, b):} before each function other than the main program; \emph{optimized text} is the optimized program printed the same way. The optimized text and the \clir{} package encode the same optimized program, so comparing compressors on the optimized text with \clir{} isolates the effect of the encoding.

\subsection{Results}

\subsubsection{Instruction reduction}
Table~\ref{tab:opt} and Fig.~\ref{fig:reduction} show the instruction counts before and after optimization. With all seven passes, the demonstration programs lose \nredSMin\% (S5) to \nredSMax\% (S4) of their instructions, \nredMeanS\% on average, but the kernels only \nredKMin\% to \nredKMax\%, \nredMeanK\% on average. The demonstration programs have no input, so folding and SCCP turn almost every value into a literal and dead-code elimination removes the literal loads. In the kernels, values that depend on input, parameters and call results are unknown at compile time; the passes mainly remove the literal temporaries and copies that the TAC generator produces. The reductions of the demonstration programs are therefore an upper bound that programs with input do not reach. The five passes of the first release reach \nredBaseSMin\% to \nredBaseSMax\% and \nredBaseKMin\% to \nredBaseKMax\%. The new passes help most where values flow around loops: S5 keeps \nsFiveBase{} of its \nsFiveRaw{} instructions with the five passes and \nsFiveAll{} with all seven, because copy propagation removes the copies that carry the Fibonacci recurrence from one iteration to the next. Value numbering found nothing to replace in any benchmark, since folding had already turned the repeated expressions of S3 into constants.

\subsubsection{Size reduction}

The \clir{} package is \nclirRawSMin\% to \nclirRawSMax\% smaller than the raw TAC text on the demonstration programs and \nclirRawKMin\% to \nclirRawKMax\% on the kernels, and \nclirOptSMin\% to \nclirOptSMax\% and \nclirOptKMin\% to \nclirOptKMax\% smaller than the optimized text. These sizes include everything a decoder needs: literal operands are stored in the constant pool, the pool contains only the literals the code refers to, and the block and function structure is explicit. In the first version of this article, literal operands were register indices whose values were not written, and the pool was written as built by the front end; S4 then took 61 bytes, 47 of them for a pool that no instruction used. The optimized text is not always smaller than the raw text; it is larger for \ntextGrownCount{} of the \nbenchCount{} benchmarks (\ntextGrownIds). SSA conversion appends a version number to every variable occurrence (\texttt{x} becomes \texttt{x\_0}) and adds $\phi$-lines such as \texttt{i\_1 = phi(BB3: 0, BB5: t13\_0)}, so the SSA text is \nssaTextGrowMin\% to \nssaTextGrowMax\% longer than the raw text, although it has only \nssaInstrGrowMin\% to \nssaInstrGrowMax\% more instructions. The optimized-text column therefore reflects the spelling of SSA names, not the amount of code; \clir{} numbers names and is not affected.

\subsubsection{Comparison with general-purpose compressors}
To isolate the effect of the encoding, we compressed the optimized text, which describes the same optimized program as the \clir{} package, with three widely used general-purpose compressors: Brotli~\cite{alakuijala2019brotli}, Zstandard~\cite{collet2021zstd} and xz~\cite{tukaani2024xz}. Table~\ref{tab:compare} and Fig.~\ref{fig:compare} show that \clir{} is smaller than the best of the three on every benchmark: by \ncmpFramedSMin\% to \ncmpFramedSMax\% on the demonstration programs and by \ncmpFramedKMin\% to \ncmpFramedKMax\% on the kernels. The smallest margin is S1, whose package consists mainly of string literals. Against the raw text, the baseline of the first version of this article, the margins are \ncmpRawTextSMin\% to \ncmpRawTextSMax\% and \ncmpRawTextKMin\% to \ncmpRawTextKMax\%; they mix the effect of optimization with that of encoding and are not used for the comparison.

For inputs of a few hundred bytes, container headers are a large share of the output. Without them, that is, with Zstandard frames that omit the magic number, checksum, content size and dictionary id, and with raw LZMA2 instead of the \texttt{.xz} format (Brotli streams and raw DEFLATE have no container to remove), \clir{} is still \ncmpHdrlessKMin\% to \ncmpHdrlessKMax\% smaller on the kernels and smaller on \ncmpHdrlessSWins{} of the seven demonstration programs; the exception is \nhdrLosers. Many small files of the same kind are best compressed with a shared dictionary. With a \ndictBytes-byte dictionary trained on \ndictTraining{} random programs and not counted per file, Zstandard or DEFLATE beat \clir{} on \ndictLosers. These are the smallest programs, whose optimized text consists almost entirely of tokens the dictionary contains. On all kernels, \clir{} remains \ncmpDictKMin\% to \ncmpDictKMax\% smaller.

The two stages remove different kinds of redundancy. A compressor finds repeated byte strings but must keep every instruction; the optimizer removes instructions, and \clir{} replaces names and literals by small indices. Both can be combined. On the \nscaleCmpCount{} random programs of the scaling study, \clir{} alone was smaller than the best compressor applied to the optimized text in \nscaleCmpWins{} cases (from \nscaleCmpMin\% to \nscaleCmpMax\%); in the largest programs the compressors find enough repetition to win. Brotli applied to the \clir{} package was smaller than the best compressor applied to the optimized text in \nscaleClirBrotliWins{} of the \nscaleCmpCount{} programs.

\subsubsection{Entropy-coding overhead}
Canonical Huffman coding made \nhuffHelpedBench{} of the \nbenchCount{} packages smaller, including \nhuffHelpedKernels{} of the ten kernels, by up to \nhuffGainKMax\%; its header is \nhuffHeaderShareMin\% to \nhuffHeaderShareMax\% of the output (Table~\ref{tab:size}). With the frequency-table header of the first release, every package became \nfreqGrowMin{} to \nfreqGrowMax{} times larger. Fig.~\ref{fig:scaling} shows where entropy coding starts to help. Across the \nscalePrograms{} random programs of the scaling study, canonical coding was no smaller than its input for every package of up to \nhuffLo{} bytes and smaller for every package of \nhuffHi{} bytes or more; with the frequency table, the threshold lay between \nfreqLo{} and \nfreqHi{} bytes. In \nfullAlphabet{} of the programs all 256 byte values occur, so the canonical header takes \nfullAlphabetCanonHeader{} bytes against 1287 for the frequency table, and the entropy of the packages larger than 1~kB lies between \nentropyMin{} and \nentropyMax{} bits per byte. Applied program by program, \eqref{eq:breakeven} classifies \nhuffModelCorrect{} of the \nscalePrograms{} programs correctly for the canonical header and \nfreqModelCorrect{} for the frequency table. The break-even point of about 5.7~kB reported in the first version of this article was thus caused by the header, not by Huffman coding. \subsubsection{Correctness}
On all \nbenchCount{} benchmarks, the raw TAC, the SSA form and the optimized form printed identical values; for the kernels these equal the output of the native build and of the Java translation. Every \clir{} package was decoded without any table from the encoder, was equal to the optimized program up to a consistent renaming of variables, labels and blocks, and printed the same values when its control-flow graphs were rebuilt and executed. Every Huffman package matched \eqref{eq:huff} exactly and decompressed to its input. Every columnar container decoded back to the optimized instructions. In the first release, the container stored 0 for the 7 of the 14 $\phi$-arguments of S2, S5, S6 and S7 that are defined later in the linear order, and its round-trip check compared the encoder's own intermediate records, which a lossy encoding reproduces; signed distances remove the loss, and the check now compares instructions.

Table~\ref{tab:diff} summarizes differential testing on \ndiffPrograms{} random programs with \ndiffMinInstr{} to \ndiffMaxInstr{} raw instructions each, \ndiffTotalInstr{} in total. The SSA form agreed with the raw TAC on all of them. With the folder of the first release, the optimized form disagreed on \ndiffReleasedDiffer{} programs (\ndiffReleasedRate\%), an agreement rate of only \ndiffReleasedAgree\%. The folder evaluated integer \texttt{/} and \texttt{\%} with Python's floor rule, whereas C truncates toward zero, so an expression whose value is $-31$ reduced modulo 1000 folded to 969 instead of $-31$; every one of these divergences disappears when both programs are run with the floor rule. \subsubsection{Threats to validity}
The demonstration programs are small and were written to show the passes, and they have no input; the kernels read input and call functions, but they are short, written for this study and limited to a subset of C without arrays or pointers, so the size of real programs remains to be measured. Integers are unbounded in the pipeline and in the reference interpreters, while C integers overflow; the kernels stay within 32 bits, which their native execution confirms. The shared dictionary was trained on random programs that resemble the demonstration programs, which favors the compressors on those programs. The comparison with Java class files and LLVM bitcode measures formats that carry more information than \clir{}. The reference interpreters were written for this study and could share a misconception with the pipeline; native execution of the kernels and their Java translations guard against this for the kernels. All times were measured on one machine.

\section{Conclusion and Scope for Future Work}
\label{sec:conclusion}
%% ===========================================================================
This article presented an SSA-based pipeline that compacts three-address code by optimizing it first and encoding it second, and checked every reported number with released evaluation scripts.

Existing methodologies either shrink native code inside large production compilers or compress intermediate code as an opaque file with general-purpose compressors.

The proposed method removes instructions with seven SSA passes, including SCCP and copy propagation, and writes the rest as a self-describing bytecode with one opcode byte, tagged LEB128 operands and a pruned constant pool. Its advantage is that each stage is measured separately, the encoding is compared with compressors applied to the same optimized program, and behavior is verified.

The system was implemented in Python with a Cytoscape.js web front end, and evaluated with independent decoders, reference interpreters, native execution of C kernels and differential testing.

Optimization removed \nredSMin\% to \nredSMax\% of the instructions of seven demonstration programs without input, but only \nredKMin\% to \nredKMax\% of ten kernels that read input and call functions. Against the best of Brotli, Zstandard and xz applied to the optimized text, the \clir{} bytecode was \ncmpFramedSMin\% to \ncmpFramedSMax\% smaller on the demonstration programs and \ncmpFramedKMin\% to \ncmpFramedKMax\% smaller on the kernels; without container headers it lost only on S1, and with a shared dictionary the compressors won on \ndictLosersCount{} of the seven small demonstration programs, while \clir{} stayed \ncmpDictKMin\% to \ncmpDictKMax\% smaller on the kernels. Java class files and LLVM bitcode of the kernels were \njavaRatioMin{} to \njavaRatioMax{} and \nbitcodeRatioMin{} to \nbitcodeRatioMax{} times larger, mostly because of metadata and fixed per-file costs. With canonical code lengths instead of a frequency table, Huffman coding paid off above about \nhuffHi{} bytes instead of 5.7~kB. Differential testing showed that the folder of the first release miscompiled \ndiffReleasedDiffer{} of \ndiffPrograms{} random programs; the corrected pipeline agreed on all of them and on \ndiffInputPrograms{} programs with input.

Future work will extend the language with arrays and memory, so that kernels from an established C benchmark suite can be translated, and will measure the pipeline on them. The entropy stage will use a pre-trained or context-modeling coder, and the bytecode will be compared with WebAssembly binaries produced by a WebAssembly toolchain.
